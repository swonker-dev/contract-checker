# План работы над MVP ИИ агента для проверки трудовых договоров

## 1 Цель MVP

Создать рабочий прототип, который принимает стандартный трудовой договор, разбивает его на смысловые части, находит релевантные положения законодательства РФ и формирует отчёт о потенциальных нарушениях и неоднозначных формулировках.

MVP должен быть понятен следующим участникам проекта и допускать замену отдельных компонентов без полной переработки системы.

## 2 Границы MVP

### Поддерживается

- Стандартный бессрочный трудовой договор.
- Работодатель — российская организация.
- Работник — совершеннолетний гражданин РФ.
- Обычная офисная работа с нормальными условиями труда.
- Текстовые файлы DOCX и PDF.
- Нормативная база из выбранных статей Трудового кодекса РФ.
- Ручное обновление нормативной базы через административный интерфейс или служебную команду.
- Проверка каждого пункта договора с присвоением статуса и формированием комментария.

### Не поддерживается в первой версии

- Другие виды договоров.
- Срочные, дистанционные, вахтовые и иные специальные трудовые отношения.
- Иностранные и несовершеннолетние работники.
- Сканированные документы и OCR.
- Судебная практика, региональные соглашения и локальные акты работодателя.
- Автоматическая Judge LLM. Precision и recall считаются по
  ручной разметке демонстрационных кейсов.
- Автоматическое получение новых редакций законодательства.
- Полноценное юридическое заключение.

Если документ не соответствует области MVP, система должна сообщить об этом до начала проверки.

## 3 Общий процесс обработки

1. Пользователь загружает DOCX или PDF.
2. Система извлекает текст и сохраняет структуру документа, если она доступна.
3. Определяется, является ли документ поддерживаемым трудовым договором.
4. Персональные данные заменяются плейсхолдерами.
5. Договор разбивается на чанки по разделам и нумерованным пунктам.
6. Для каждого чанка выполняются детерминированные проверки однозначных числовых ограничений.
7. Если правило не сработало, выполняется семантический поиск по нормативной базе.
8. В LLM передаются чанк и несколько наиболее релевантных нормативных фрагментов.
9. LLM определяет применимость нормы и формирует результат проверки.
10. Приложение проверяет наличие цитат, объединяет дублирующиеся замечания и формирует отчёт.

## 4 Формат результата проверки чанка

На первом этапе используется компактный машиночитаемый ответ:

```json
{
  "chunk_id": "5.2",
  "status": "warning",
  "source": "ТК РФ, статья 57",
  "contract_quote": "Оплата труда определяется работодателем",
  "law_quote": "Обязательными являются условия оплаты труда",
  "comment": "Не указан конкретный размер оклада"
}
```

Статусы:

- `ok` — применимая норма найдена, противоречие не обнаружено.
- `warning` — формулировка неполная, неоднозначная или требует проверки специалистом.
- `violation` — обнаружено прямое противоречие с переданной нормой.
- `not_applicable` — переданные нормативные фрагменты не относятся к чанку.

Числовой confidence в MVP не используется. Скор семантического поиска сохраняется только в техническом журнале и применяется для сортировки результатов поиска.

## 5 Этапы разработки

### Этап 1 Уточнение требований

Задачи:

- Зафиксировать поддерживаемый вид трудового договора.
- Определить перечень первоначальных статей ТК РФ.
- Согласовать статусы и обязательные поля результата.
- Настроить выбранную LLM GigaChat 2 Lite через GigaChat REST API.
- Подготовить несколько демонстрационных договоров без реальных персональных данных.

Результат этапа:

- Утверждённая спецификация MVP.
- Список нормативных источников.
- Набор демонстрационных сценариев.

### Этап 2 Создание каркаса проекта

Задачи:

- Создать структуру репозитория.
- Подготовить проект к публикации в отдельном репозитории GitHub без привязки к существующему домашнему репозиторию.
- Настроить конфигурацию приложения и переменные окружения.
- Реализовать единый клиент для выбранной LLM.
- Добавить журналирование без записи исходных персональных данных.
- Подготовить команды локального запуска.

Предлагаемые модули:

```text
app/
  document_parser/
  document_classifier/
  anonymizer/
  chunker/
  knowledge_base/
  retrieval/
  llm_client/
  analyzer/
  report/
  ui/
tests/
evals/
data/
  regulations/
```

Результат этапа:

- Приложение запускается локально.
- Конфигурация модели не хранит API ключ в репозитории.
- Компоненты имеют отдельные интерфейсы.

### Этап 3 Нормативная база

Задачи:

- Скачать выбранные актуальные статьи ТК РФ из официального источника.
- Сохранить исходный текст и ссылку на источник.
- Добавить метаданные редакции и периода действия.
- Разбить статьи на небольшие смысловые фрагменты.
- Реализовать добавление, активацию и архивирование версий.
- Построить embeddings нормативных фрагментов.

Результат этапа:

- Локальная версионированная нормативная база.
- Возможность обновить источник и перестроить поисковый индекс.

### Этап 4 Загрузка и подготовка договора

Задачи:

- Извлекать текст из DOCX.
- Извлекать текст из текстовых PDF.
- Проверять тип файла и ограничения размера.
- Определять, похож ли документ на трудовой договор.
- Реализовать базовую анонимизацию.
- Сохранять номера разделов и пунктов.
- Разбивать документ на структурные чанки.

Результат этапа:

- Договор преобразуется в список чанков с идентификаторами.
- Документы вне области MVP отклоняются с понятным сообщением.
- Основные персональные данные не передаются в LLM.

### Этап 5 Семантический поиск

Задачи:

- Вычислять embedding каждого чанка договора.
- Сравнивать его с embeddings нормативных фрагментов.
- Возвращать несколько наиболее близких норм.
- Сохранять внутренние similarity scores.
- Предусмотреть интерфейс для последующей замены реализации поиска.

Для первой версии достаточно полного перебора embeddings через NumPy. FAISS можно добавить позднее при увеличении нормативной базы.

Результат этапа:

- Для каждого чанка возвращаются релевантные нормативные фрагменты с метаданными.

### Этап 6 Проверка правилами и через LLM

Задачи:

- Проверять правилами прямые числовые ограничения: рабочую неделю свыше 40 часов,
  отпуск менее 28 дней, выплату зарплаты раз в месяц и испытание свыше трёх
  месяцев для обычного работника.
- До вызова LLM проверять весь договор на отсутствующие или неконкретные место
  работы, трудовую функцию, размер оклада и режим работы.
- Разработать консервативный системный промпт.
- Передавать модели только текущий чанк и найденные нормы.
- Ограничить размер и формат ответа.
- Запретить статус `violation` без прямых цитат и объяснения противоречия.
- Проверять, что возвращённые цитаты действительно присутствуют во входных текстах.
- При ошибке формата повторять запрос с исправляющей инструкцией не более одного раза.

Результат этапа:

- Каждый чанк получает проверяемый структурированный результат.
- Неподтверждённые выводы не попадают в категорию `violation`.

### Этап 7 Объединение результатов и отчёт

Задачи:

- Объединять результаты всех чанков.
- Удалять дублирующиеся замечания.
- Сохранять связь замечания с исходным пунктом договора.
- Сортировать результаты по статусу.
- Формировать человекочитаемый отчёт.
- Показывать нормативные ссылки, цитаты и комментарии.

Результат этапа:

- Пользователь получает итоговый отчёт по договору.
- Технические результаты `ok` и `not_applicable` доступны для диагностики, но не перегружают основной отчёт.

### Этап 8 Интерфейс и администрирование

Задачи:

- Сделать страницу загрузки договора.
- Показывать ход обработки и итоговый отчёт.
- Добавить страницу управления нормативными источниками.
- Реализовать загрузку новой редакции и перестроение индекса.
- Показывать активные и архивные версии источников.

Статус: реализованы веб-загрузка JSON, валидация, архивирование, повторная активация и
ленивое перестроение индекса. Авторизация админки остаётся за границами локального MVP.

Результат этапа:

- MVP можно использовать без запуска отдельных скриптов вручную.

### Этап 9 Ручная проверка MVP

Задачи:

- Подготовить несколько корректных договоров.
- Добавить договоры с очевидными пропусками и рискованными формулировками.
- Зафиксировать ожидаемые замечания в машиночитаемом eval-наборе.
- Автоматически считать precision и recall для правил и полного агента.
- Проверить устойчивость к разным названиям разделов.
- Проверить отказ на документах другого типа.
- Сохранить результаты для последующего формирования golden dataset.
- При необходимости проверить отчёты во внешней Judge LLM вручную.

Результат этапа:

- Список обнаруженных ограничений и ошибок.
- Первые материалы для будущего golden dataset.

### Этап 10 Документация и передача проекта

Задачи:

- Описать локальный запуск.
- Описать конфигурацию LLM.
- Описать добавление нормативного источника.
- Описать формат результата анализа.
- Добавить схему компонентов и поток данных.
- Зафиксировать ограничения MVP и направления развития.

Результат этапа:

- Следующий участник может запустить проект, заменить модель и добавить новый тип документа.

## 6 Критерии готовности MVP

MVP считается готовым, если:

- Пользователь может загрузить текстовый DOCX или PDF.
- Пользователь выбирает профиль трудового договора перед загрузкой; автоматическая
  классификация фактического содержимого отложена.
- Договор разбивается на понятные чанки с сохранением номеров пунктов.
- Персональные данные базовых типов анонимизируются до вызова LLM.
- Для каждого содержательного чанка выполняется поиск нормативных фрагментов.
- LLM возвращает результат установленного формата.
- `violation` не создаётся без существующих цитат из договора и нормы.
- Пользователь получает отчёт с замечаниями и нормативными основаниями.
- Администратор может заменить или добавить нормативный источник и перестроить индекс.
- Проект запускается по документированной инструкции.

## 7 Основные риски

- Модель может находить нарушения там, где их нет.
- Нужное условие может находиться в другом чанке.
- Извлечение текста из PDF может нарушать порядок абзацев.
- Анонимизация может удалить сведения, необходимые для проверки.
- Нормативный источник может потерять метаданные редакции.
- Разные формулировки договора могут снижать качество поиска.
- Без golden dataset нельзя обоснованно калибровать confidence и пороги similarity.

Для MVP эти риски снижаются консервативными статусами, обязательными цитатами, сохранением технических логов и ручной проверкой демонстрационных примеров.

## 8 Отложенные улучшения

- Расширенный golden dataset, проверенный юристом.
- Калибровка confidence и порогов поиска.
- Полнотекстовый поиск и гибридный reranking.
- FAISS или отдельная векторная база данных.
- OCR для сканов.
- Автоматическая проверка соответствия содержимого выбранному типу документа.
- Поиск противоречий между удалёнными пунктами.
- Автоматическое обновление законодательства.
- Поддержка дополнительных типов договоров.
- Проверка по судебной практике и официальным разъяснениям.
- Экспорт отчёта в DOCX или PDF с подсветкой исходного текста.

## 9 Решения которые необходимо подтвердить

- LLM подтверждена: GigaChat 2 Lite, идентификатор модели API `GigaChat-2`.
- Интерфейс подтверждён: каталог типов на главной странице и отдельная страница
  проверки выбранного типа поверх FastAPI.
- Какие статьи ТК РФ войдут в первый нормативный пакет.
- Где будет запускаться MVP: локально, на учебном сервере или в облаке.
- Исходные загруженные договоры не сохраняются: временный файл удаляется после
  анализа; статус и обезличенный результат сохраняются в SQLite.
- Какой формат итогового отчёта требуется для демонстрации проекта.

## 10 Текущий baseline качества

На 27 сентября 2026 года подготовлены 20 демонстрационных договоров: 10 корректных
и 10 проблемных. В ручной разметке зафиксировано 31 ожидаемое замечание. Договоры 06-10 не
подгонялись под текущие детерминированные правила.

Первый прогон только числовых детерминированных правил:

- precision: `1.000`;
- recall: `0.542`;
- найдено 13 из 24 ожидаемых замечаний;
- ложных срабатываний на демонстрационном наборе нет.

Полный прогон правил и GigaChat 2 Lite:

- precision: `0.607`;
- recall: `0.708`;
- найдено 17 из 24 ожидаемых замечаний;
- всего агент выдал 28 замечаний.

После добавления проверок обязательных условий всего договора:

- precision rule-only: `1.000`;
- recall rule-only: `0.792`;
- найдено 19 из 24 ожидаемых замечаний;
- ложных срабатываний на демонстрационном наборе нет.

Полный baseline с GigaChat выше был получен до добавления этого слоя и пересчитывается
при следующем полном прогоне.

Текущий rule-only baseline на всех 20 договорах:

- precision: `0.541`;
- recall: `0.645`;
- совпало 20 из 31 ожидаемого замечания;
- всего правила выдали 37 замечаний.

Падение метрик считается полезным результатом: оно показывает переобучение на первые шаблонные кейсы
и необходимость семантической проверки синонимов, составных условий и нетипичной структуры.

Оставшиеся кейсы — неполные и неоднозначные условия, нестандартные формулировки
и отсутствующие условия — оставлены семантическому слою с GigaChat.
